# خطة مزامنة التارزي بين أجهزة المحل

## الحالة
- المرجع الثابت: APK / build 34.
- فرع التطوير: `feature/shared-device-sync`.
- لم تُعدّل النسخة المرجعية أو ملف التطبيق الرئيسي.
- التخزين الحالي في `localStorage` تحت المفتاح `tl_db`، ويشمل `customers` و`orders` و`seq` و`set`.
- لا توجد حاليًا قاعدة بيانات مشتركة أو مصادقة أجهزة في تطبيق التارزي.

## الهدف
تمكين العامل داخل المحل من العثور على بيانات الزبائن والطلبات والمقاسات حتى عندما يكون هاتف الخياط خارج المحل، مع الحفاظ على العمل المحلي دون إنترنت.

## التصميم المقترح
1. **قاعدة مشتركة مخصصة للتارزي**: مشروع Supabase منفصل خاص بالتارزي، وعدم إعادة استخدام مشاريع المدرسة أو الحضور أو غيرها.
2. **هوية للمحل**: كل سجل مرتبط بمعرّف محل `shop_id`، ولا يرى العامل إلا بيانات المحل الذي انضم إليه.
3. **صلاحيات للأجهزة/العمال**: مالك المحل يربط الأجهزة برمز انضمام محدود الصلاحية؛ لا توضع مفاتيح الخدمة السرية داخل APK أو HTML.
4. **مزامنة مرحلية**: تنزيل التغييرات الجديدة، ثم إرسال العمليات المحلية المعلقة، مع معرف فريد لكل عملية لتجنب التكرار.
5. **تخزين محلي مستمر**: تبقى `tl_db` النسخة المحلية، وتعمل الشاشات دون اتصال. تُعرض حالة واضحة: متصل، غير متصل، تغييرات بانتظار المزامنة، أو فشل المزامنة.
6. **منع الكتابة فوق البيانات**: لا يُستبدل كامل `tl_db` تلقائيًا ببيانات الخادم. تُدمج السجلات باستخدام معرّفات ثابتة ونسخ/أوقات تعديل، وتُعزل التعارضات للمراجعة بدل حذف أي سجل.
7. **النسخ الاحتياطي**: تبقى وظيفة JSON الحالية، ويُجرى تصدير نسخة قبل أول ربط. لا تُرسل بيانات زبائن إلى GitHub ولا إلى سجل البناء.

## مراحل التنفيذ والقبول
### المرحلة 1 — الأساس الآمن
- إعداد مشروع Supabase مستقل للتارزي.
- تصميم الجداول والسياسات: المحلات، عضوية العمال/الأجهزة، العملاء، الطلبات، وسجل تغييرات المزامنة.
- فرض Row Level Security واختبار منع الوصول المتبادل بين محلات مختلفة.

### المرحلة 2 — محرك المزامنة
- إنشاء طبقة مستقلة بين واجهة التطبيق والتخزين الحالي.
- إضافة معرفات مستقرة للسجلات والعمليات، مع ترحيل يحافظ على البيانات القديمة.
- دعم إعادة المحاولة دون تكرار، وانقطاع الاتصال، وتعارض التعديلات.

### المرحلة 3 — واجهة داخل التطبيق
- قسم «مزامنة أجهزة المحل» في الأدوات.
- إنشاء محل/ربط جهاز/إلغاء جهاز، مع رمز ربط آمن.
- عرض آخر مزامنة وحالة الطابور وزر مزامنة يدوي.
- صلاحيات عرض الطلبات وتعديلها وفق الدور.

### المرحلة 4 — الاختبارات
- جهازان على الشبكة نفسها مع الإنترنت.
- جهازان دون إنترنت ثم إعادة الاتصال.
- إنشاء عميل وطلب على الجهاز الأول وظهورهما على الثاني.
- تسجيل دفعة أو تعديل حالة طلب من جهاز، والتحقق من اتساق الجهاز الآخر.
- اختبار تكرار الطلبات والتعارض وإعادة تشغيل التطبيق.
- التحقق من أن التثبيت/التحديث لا يمحو `tl_db`.
- لا يُرقّى البناء ولا يُستبدل build 34 قبل اجتياز الاختبارات.

## قيد مهم
المزامنة السحابية تحتاج إنترنت وقت تبادل البيانات. العمل دون إنترنت يعني أن كل جهاز يستخدم نسخته المحلية مؤقتًا، ثم تتم المزامنة عند عودة الاتصال. مشاركة فورية بلا إنترنت تتطلب شبكة محلية وخدمة اتصال إضافية، وهي مسار منفصل وليست ميزة تلقائية في Supabase.

## معيار عدم الإضرار
- عدم حذف بيانات أو استبدالها بصمت.
- عدم وضع مفاتيح إدارية سرية في التطبيق.
- عدم تغيير `main` أو بناء 34 أثناء التطوير.
- كل اختبار يوضح ما نُفذ فعلًا وما لم يُختبر بعد.
